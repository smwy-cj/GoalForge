# 目标清单

请核对目标是否符合原意；需要时在统一意见区说明。

材料：DOC016.txt

1. 在一个应用里聚合多来源资讯，跟进商业、政治、编程三类内容。
   条件：三类的用途：炒股（商业、政治）与本职业（编程、科技股）；自评每天使用
2. 在有限时间（早晨、遛狗）内摄取尽可能多的信息。
   条件：典型时段：上班前、遛狗途中；目标为「多看条目」而非「读完全文」
3. 把多条摘要拼起来，形成对全球局势的整体判断。
   条件：自述为阅读逻辑：先广度后串联
4. 用发布时间判断消息是否已被美股消化，据以推测当日走势。
   条件：区分发布时刻（原媒体）与接收时刻（进入 Feedly）；例：日本股市消息若发布于 3 小时前，美股尚未反映
5. 能按「媒体 × 类别」的粒度调整推荐，而不是只能屏蔽整个媒体。
   条件：现状：只能整体取消订阅某媒体，无法只屏蔽其某类内容
6. 跳转到原文之前，先提示该站需要订阅或登录。
   条件：典型：纽约时报几乎每篇都要登录再订阅；期望省掉一次往返
7. 从外链返回时不自动刷新，保留已看/未看的浏览进度。
   条件：现状：返回即刷新，进度全丢，需从头再来；后果：有时索性关掉应用
8. 减少同一事件被多家媒体重复推送、反复出现的情况。
   条件：成因归为推荐算法：不感兴趣的新闻换一家媒体又出现；他靠认图片判断是否重复，快速划过
9. 收藏（read later）里的文章按类别分组，便于按主题回看。
   条件：现状：仅按时间倒序，可加星标
10. 提供可听的朗读模式，用有语气的语音而非机械音。
   条件：场景：开车、健身、遛狗等无法盯屏的时段；自评这是最想要的功能
11. 保持应用极简，不堆叠多余功能。
   条件：视为该应用最被认可的优点之一；与 C002 的快速摄取直接相关
12. 出错时给出普通读者能看懂的提示，而不是 HTTP 状态码。
   条件：现状：源站 API 异常时直接把 400/500 显示在文章位置；他认为只有开发者能看懂
13. 能就最新热点与同事展开讨论（信息更新到可社交的程度）。
   条件：被问及「怎样算一次成功的阅读」时给出；受访者补充这是此前未提到的需求
