# 目标清单

请核对目标是否符合原意；需要时在统一意见区说明。

材料：DOC022.txt

1. 在任意机器上都能改代码，尤其是没有图形界面的服务器。
   条件：选择 vim 的实用理由：机器上不一定装了别的编辑器；服务器只能通过终端访问，无法运行图形界面编辑器
2. 把个人配置带到每一台机器，让各处环境一致。
   条件：做法：维护一份 vim 配置文件，复制到服务器即可复现本地体验；这也是他称 vim「轻」的第二层含义
3. 本地环境可深度定制：外观、快捷键、语法主题都按自己习惯来。
   条件：做法：装一堆插件、改界面「让它看起来很酷」；快捷键自定义到 ctrl+P / ctrl+E / 反斜杠+P
4. 全部操作靠键盘完成，手不离键盘以提升效率。
   条件：自述这是 vim 效率优势的核心；自评「酷」的旧动机已淡化，但效率理由保留
5. 在大型项目里按文件名快速定位文件，并能跨文件全局搜索。
   条件：手段：模糊搜索插件（fuzzy finder）+ 文件树
6. 在同一个终端窗口内分屏：一边编辑、一边执行，立刻看到运行结果。
   条件：工具：tmux 分左右两栏（命令行 / vim）；修改后切到命令行执行，结果立刻可见
7. 从编码、提交、评审到部署与线上监控，尽量在同一工具内完成。
   条件：现状对比：终端工作流需频繁切浏览器（GitHub/Jenkins/AWS/Kibana）；VS Code 靠各类扩展把整条流水线收进编辑器
8. 编辑器必须支持插件/扩展，好把工具装配到满足自己的全部需求。
   条件：理由：裸编辑器只负责改文本，开发者需要的远不止这些
9. 装扩展应像应用商店一样：可搜索、可看文档与评分，再一键安装。
   条件：对照：vim 插件要翻 GitHub 页面、往配置文件里粘代码
10. 编辑器背后有活跃社区，遇到问题能查到别人的解法。
   条件：他自己的 vim 学习路径：看 YouTube、Stack Overflow、问 GPT，几乎不读官方文档
11. 写代码时获得语言相关的语法高亮与缩进支持，让代码更易读。
   条件：他以此区分「代码空间」与记事本；承认这是编辑器的基础能力，不含个性化
