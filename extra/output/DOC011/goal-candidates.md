材料：DOC011.txt

1. 与队友异步协作修改同一份代码，完成课程与项目作业。
   条件：主要身份为学生与助教；队友同时有仓库写权限，无法约到共同工作时间时靠异步协作
2. 代码合并进主分支前必须经他人审查，防止未审改动进入主干。
   条件：审查由同一仓库的其他协作者执行；不达标可拒绝合并
3. 改动按小步增量提交，减少协作者每次要审查的内容量。
   条件：自述为个人偏好，非团队强制；独自开发时反而倾向大 PR，因为没人要审
4. 能回看仓库的变更历史，包括每次提交改了什么、由谁改。
   条件：PR 不会被删除，保留在列表中可追溯
5. 代码安全保存在云端，本机损坏或丢失时可换机拉取继续。
   条件：也支持协作者各自分支存放工作，不影响主仓库
6. 检索并阅读他人公开仓库的代码。
   条件：可按关键词、文件名、变量名、语言筛选；范围含仓库、PR、issue、讨论区与用户名
7. 用看板跟踪任务状态与分工（backlog → 待办 → 进行中）。
   条件：任务以 issue 形式建立，含标题、描述与被指派人；团队开会决定指派后再移入待办列
8. PR 与看板 issue 关联，合并后看板状态自动更新。
   条件：依赖项目已链接到对应仓库；通过 resolves / #issue 关键词关联
9. GitHub Actions 的官方文档更易查，并提供讨论区或博客。
   条件：现状：官方文档「broad」且难找，多数信息来自 Stack Overflow 等外部来源
10. 以可视化方式呈现分支创建与合并的历史，而不只是线性提交栈。
   条件：自评为 nice-to-have，非必需；期望同时看到分支内的 issue 与时间线
11. 内置 AI 助手，辅助代码审查与操作引导，并帮用户用上平台已有的资源。
   条件：动机：独立开发者只能自己审自己，缺少第二意见；期望覆盖：审查建议、PR 与 actions 文件的操作引导
