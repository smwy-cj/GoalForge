# 简明目标提取与 KAOS 模型修改方案

日期：2026-10-18。状态：修改方案，尚未改动 Skill、工具、现有模型和审核草稿。

## 一、最终体验

使用者提供资料，助手完成提取、核对和 KAOS 核心子集建模，最后交付一份目标层次清楚、文字简短、可直接给意见的 HTML。用户不需要学习类别、填写技术文件、阅读全部中间报告或检查两两目标关系。

采用 KAOS 的核心精化机制，而非要求用户操作完整形式化方法。由 Skill 处理目标、精化组、责任、条件与障碍；无形式化证明时明确这是概念层模型，不宣称完成形式验证。

四项 Skill 保留，顺序衔接由当前助手负责。此次不增加独立分类 Skill、统一入口 Skill、模型 API 或 Agent 调度服务。

## 二、分类精简：只把目标列为正式候选

### 用户看到什么

- 目标清单只列“希望达到或保持的结果”，不显示主类、子类、类别解释和英文标签。
- 动作、偏好、困难、规则与普通事实不逐项铺成另一套候选清单；与目标有关的内容保留为其依据、条件或问题。
- 只有影响判断的不确定性才提示，例如“这是根据原文推断，请确认”“完成条件尚不明确”。

### 内部如何处理

1. 取消新契约中强制的五主类与单选 subtype；新的目标候选数组只包含目标。
2. 保留目标表述、主体、必要条件、原文依据、直接表达或推断、待确认问题与稳定 ID。
3. 非目标内容保留在源文与相关目标引用中；仅当它影响建模时，形成简短的条件、障碍或问题记录。不再给每段操作、偏好或普通事实单独编号分类。
4. 暂时无法确定是否为目标的内容放入待确认问题，不强行纳入正式目标。缺页、不可读资料和关键识别错误始终保留范围说明。
5. 达成、维持、避免等模式仅在建模需要时记录；不要求所有目标都完成多维标签。设计补全建议与提取结果分开，默认不扩写新需求。

这是减少分类工作，不是先把原文摘要化。先忠实读取，随后只提取与本次任务有关的目标和必要依据。

## 三、目标表达：短句但保留关键含义

推荐表述为“主体＋希望得到的结果＋必要条件”。默认一句话，避免把分类理由、方法解释和证据塞进标题。

- 原文没有量化指标，不补造数值；关键条件未知时列为待确认。
- 否定、范围、时限和数量不得为了缩短而丢失。复杂条件可放在紧邻目标的展开内容中，审核时能完整读取。
- 合并重复目标须核对主体和情境，保留来源映射；不能为了减少节点把不同要求揉在一起。
- 不凭动作动词判定目标。“打开页面”与“能够获得所需信息”仍按实际上下文判断。
- 内部完整表述与用户看到的表述保持同义；默认尽量使用同一句话，不额外生成另一套可能失真的摘要目标。

## 四、KAOS 核心建模：先建目标层级，必要时补充条件

### 精化关系作为一组保存

| 内部表达 | 用户看到的说明 | 建立条件 |
|---|---|---|
| AND 精化组 | 以下各项都需满足 | 在明确领域假设下，子目标共同满足足以实现父目标 |
| 替代精化方案 | 以下方案任选一种即可 | 每个方案均可满足父目标；方案内部可以再包含 AND 组 |
| 责任分配 | 由谁负责 | 有来源或已确认的分工，未知时不编造 |
| 必要假设、约束 | 适用条件 | 影响精化或目标含义时呈现 |
| 障碍 | 可能阻碍什么 | 说明其影响的目标；普通抱怨不自动等同于已证实障碍 |

主视图展示目标与成立的精化组。一般相关联系不进入默认图，必要解释可放到详情；不把“有帮助”“主题相似”或“先后执行”当作精化。

### 不强行造树

- 顶层是资料确实支持的高层目标，不为统一图形自动发明一个总目标。
- 目标层数按语义决定，通常先展示一至两层；不固定要求每个模型必须有三层。
- 原文没有中间层时，可直接连接有依据的层级；资料不足时保留独立目标或未完成的建模问题。
- 可提出少量关键补全问题或明确标注的父目标建议。未确认建议不伪装为原文目标，也不据此宣称完整精化成立。
- 共享子目标使用“也服务于……”引用；浏览树允许多处引用同一 ID，编辑与审核仍对应同一个目标。底层保留 DAG，不复制成多个独立目标。
- 阅读分组如确有必要，标明它只是导航；不能用普通标题分组冒充 KAOS 父目标。

### 减少关系判断

停止把枚举全部 n(n−1)/2 目标对作为日常默认要求。按目标抽象层次、证据和上下文提出可能的父子关系，再对精化组作针对性判断，检查孤立项、遗漏与冲突。

内部记录实际评估范围；没有评估的关系不自动标记“无关系”。需要科研对比或全量分析时可显式使用旧的全对评估模式，单独计量成本。

程序负责引用、组成员、方向、循环、条件与覆盖等可执行检查；语义判断仍由模型或人完成。只有图形合法不能证明精化充分、完整或真实。

## 五、HTML 只保留一条清楚的阅读与审核路径

### 首屏

1. 资料范围与模型标题，一句说明；若有影响阅读的缺失或识别问题，简短提示。
2. 可展开的目标层级，默认打开顶层与下一层。每项以短句呈现，有必要时显示“需确认”。
3. 一个主要入口：“审核这些目标”。

取消默认展示的分类统计卡、全景关系网、关系类型筛选、全部目标对、技术编号和多组工具栏。搜索仅在规模需要时出现。

### 点击目标

按需展开：

- 这项目标的完整描述与必要条件。
- 一段主要原文依据及来源位置；其他依据再展开。
- 与上层目标的关系，以及确实需要确认的疑点。
- 三个操作：“可以／需要修改／暂不确定”。

“需要修改”先提供一个意见输入框，不让用户选择补丁、合并、拆分等技术操作；助手根据实际意见提出或执行相应修订。复杂意见仍保留可自由说明的入口。

### 层级关系怎么审

审核一个父目标时，连同其子目标与“各项都需满足／任选方案”的说明一起展示。用户可指出“缺了一项”“这些不能保证上层目标”“不应放在这里”。

内部反馈单独绑定目标或精化组，不能把对目标表述的认可自动当作对精化关系的认可。未展示的隐藏内容也不因点击“可以”而视为已审阅。

### 汇总与导出

常规进度分别说明“已看目标 X/Y”“还有 Z 个问题”，不把目标、证据和所有关系混成一个总数。目标看完不自动认可完整模型；仍可提交部分意见。

默认按钮为“导出审核意见”，旁边简短说明“导出后交回助手”。草稿保存与导入放入次级菜单。使用[导出可靠性方案](11-导出可靠性与模型易读性优化方案.md)中的文件保存、复制完整内容、文本预览与如实状态反馈。

完整确认针对实际展示并明确声明的范围。新版本仍需重新审核；有隐藏或未解决项时不将当前确认扩张为全部内容认可。

## 六、中间输出收敛

| 阶段 | 内部保留 | 默认给用户看 |
|---|---|---|
| 资料读取 | 忠实转换稿、位置映射、实际处理范围 | 仅在缺失或识别问题影响结果时提示 |
| 目标提取 | 简化的目标 JSON 与证据引用 | 请求分阶段审核时给简短候选 MD；否则直接继续 |
| 证据核对 | 位置、支持、版本绑定及必要判断 | 不单独推送逐项追溯报告；疑点汇入对应目标 |
| 建模与检查 | KAOS 精化组、映射、检查记录、未解决问题 | 不单独要求用户阅读模型草案和检查报告 |
| 最终交付 | 机器模型 JSON、实际引用附件、交付清单 | 一个 HTML 主入口、一份简短 MD 说明；JSON 可下载 |

保留每个 Skill 可复用的机器结果，但不要求普通用户逐个打开或逐阶段批准。人工文档可按需生成；未请求中间审核且不存在阻碍继续的问题时，助手连续完成流程。

简短候选 MD 仅列目标、必要疑点及统一意见区，不再逐项重复类别解释、空白意见表和完整诊断清单。需要查证时仍能定位原文。

最终默认交付 HTML、JSON 和简短 MD；SVG 改为按需导出或生成，不作为每次必须摆给用户的第四个文件。完整附件与记录保存在交付目录，需要时可获取。不得隐去影响结果有效性的资料缺失或限制。

## 七、四项 Skill 的调整

| Skill | 具体变化 |
|---|---|
| goal-extraction | 只输出正式目标与必要问题；移除强制主类、子类；默认精简文档与直接衔接 |
| goal-tracing | 保留证据核验，减少重复报告与无关上下文；问题挂到相应目标 |
| goal-model-building | 引入 KAOS 核心精化组；默认层级阅读，取消常规全对关系评估；输出简明 HTML |
| model-review | 检查精化组与责任/条件的适用性，支持目标与组的独立反馈；精简人审与变更说明 |

直接、推断、证据不足、相反证据等内部判断继续用于核对，不重新扩成用户需要学习的分类表。只有影响人工决定的状态在界面用自然语言解释。

## 八、版本兼容与实际工作量

这次涉及新目标契约、精化组与反馈对象，必须使用新 schema，不能仅改模板后沿用旧“通过”报告。

- 旧模型、草稿和反馈保持可读；现有交付不覆盖。
- 旧模型只能先映射可确定的目标、证据与一般联系。旧 refinement 不自动转成 AND／OR，旧相关关系不自动升级为层级。
- 按当前资料重新建立精化组，无法确认的继续保留问题。旧认可不转移到新语义结构。
- 模型或关系变更继续触发受影响证据、判断与检查更新；保留前轮修复的版本绑定、反馈传播及回填机制。
- 更新源 Skill 后，再按用户实际安装方式同步副本，检查实际加载版本。

为减少模型工作量，目标提取时一并保留依据，核对优先使用相关片段，关系只检查候选精化组，报告由同一数据生成。共享子目标不重复判断，修订只处理受影响对象。出现条件、否定或主体歧义时才扩展上下文，不以节省为由跳过必要查证。

## 九、实施与验收顺序

1. **冻结精简契约与文案。**先调整四项 Skill 及相关说明，给出一份小型新模型示例和机器结构；明确与旧版的区别。
2. **同步工具与界面。**实现目标契约、精化组检查、回填与反馈适配，重做简明层级 HTML；同时修复导出并保留兼容路径。
3. **受控案例验证。**覆盖 AND、替代方案、共享子目标、无可证层级、无目标、关键条件缺失、长文字、小屏，以及旧反馈不能套用新模型。
4. **新资料实际运行。**依据一份新原件生成模型，由真实用户完成“看懂层级→查看依据→提出一项修改→导出→回填→再审”。

验收关注：用户能否说出高层目标、理解子目标为什么放在下面、发现错误关系并带走意见；工程检查同时确认不丢条件、不虚构目标、不误记认可、导出文件真实可读。只有做了真实测试才能报告理解效果和成本改善，不提前宣称已经降低 token 或提高准确率。
