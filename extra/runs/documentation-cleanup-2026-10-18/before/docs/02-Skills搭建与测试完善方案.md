# GoalForge Skills 搭建与测试完善方案

日期：2026-10-15。状态：拟实施方案，未代表 Skill 或实验已经完成。

后续修订：原六 Skill 拆分方案的架构更新见[Skills 精简与最终模型输出方案](04-Skills精简与最终模型输出方案.md)。后续拟以四个顶层 Skill 承载原有能力，并由 goal-model-building 负责模型组装与最终交付；本文件保留原方案及测试思路，不能据此继续机械创建全部旧目录。

本方案依据当前仓库的研究决策、数据说明、划分清单和开发参考字段制定；沿用 S1 Skill 验证、S2 Agent 集成的阶段边界。本轮先明确搭建和验收方式，不新增数据标注结论，也不启动正式模型实验。

## 1. 当前基础与建设目标

当前已有固定版本的 34 篇访谈、2,692 轮对话、可定位的标准原文、文件哈希，以及 DOC010、DOC023、DOC031 三篇开发参考。开发参考包含 27 个目标和 111 个目标对，其中 19 对不确定，关系确认程度不同。31 篇储备没有本项目完整参考标注，独立测试集为空。

当前没有可运行的 Skill、Adapter、Runner、评测器和 Agent；历史草稿已清理，不以历史文件名推定能力存在。

建设目标是形成六个可独立调用、可组合运行、可追溯修改的 Skill，并能够回答：

1. 每个 Skill 是否遵守输入输出契约、证据和职责边界？
2. 相同模型与可比预算下，Skill 相对基础提示带来什么变化？
3. 哪些问题来自单项能力，哪些来自上游输出或流程组合？
4. 修复是否实际消除问题，以及是否损害原来正确的部分？

“文件合法”“程序能跑”“结构通过”“语义正确”“实验有效”分别验收，不互相替代。

## 2. 总体实现结构

采用三层结构：

| 层次 | 职责 | 边界 |
|---|---|---|
| Skill | 目标判断准则、任务步骤、证据规则、异常处理 | 不绑定某个模型服务，不重复实现公共逻辑 |
| Adapter / Runner | 读取 Skill、组装允许输入、调用模型、检查输出、保存运行记录 | 不把参考答案送入生成过程，不静默修改语义输出 |
| 评测与审核 | 确定性检查、人工语义审核、对照实验、失败归因 | 参考等级和不确定性显式保留 |

本方案建议以 Python 实现公共运行设施，使用 JSON Schema 定义契约、pytest 检查关键工程不变量；依赖版本在实现时锁定。首版先有离线回放适配器和一个真实模型适配器，避免同时建设多服务支持。

Skill 源码建议维护在项目的 `skills/`，便于版本管理和实验冻结。其在 Codex 中的发现或安装位置，在实施时核对目标环境；项目源码目录存在不等于已被当前会话自动加载。实验 Runner 显式加载指定版本的 SKILL.md 和所需参考，以便复现实际发送的指令。

建议目录如下；按实施阶段创建，不提前生成空目录：

```text
skills/
  goal-extraction/
    SKILL.md
    agents/openai.yaml
    references/                 # 仅放该能力需要的口径与示例
  goal-tracing/
  goal-normalization/
  goal-refinement/
  model-validation/
  model-repair/
schemas/                       # 公共契约的唯一权威定义
src/goalforge/
  contracts/
  adapters/
  runner/
  validation/
  evaluation/
tests/
  unit/
  integration/
  fixtures/                    # 合成案例，与真实访谈参考分开
evals/
  cases/                       # 场景、输入来源、审核标准
  configs/                     # 模型参数与实验设置
  rubrics/                     # 人审口径
runs/<experiment_id>/<run_id>/ # 请求、响应、中间结果、报告
docs/
```

每个 Skill 的入口只放适用范围、核心步骤、必须遵守的边界、输入输出说明和按需参考链接。复杂规则放 references，确定性操作放公共代码；只有确实可独立复用的专用工具才放入技能的 scripts。无需为六个 Skill 分别复制加载器、证据定位和图检查代码。

## 3. 先固定公共数据契约

建议新运行契约命名为 `goalforge-runtime-1`，与已有 `annotation-candidate-1` 开发参考格式分开。通过只读转换器适配旧数据，不覆盖 `goalforge-v1`。

| 对象 | 首版必要内容 |
|---|---|
| Document | document_id、document_hash、canonicalization、turns；原文内容与稳定索引 |
| Candidate | candidate_id、类别、候选表述、origin、source_ids、证据候选、推断说明 |
| Goal | goal_id、statement、origin、evidence_ids、情境属性、状态、来源候选映射 |
| Evidence | evidence_id、document_id/hash、source_id、quote、start_char/end_char、支持判断及理由 |
| PairDecision | pair_id、a/b、label、父子方向、适用条件、理由、证据、审核来源 |
| Issue | issue_id、检查规则、对象定位、严重度、确定性或语义疑点、依据、处理状态 |
| Patch | patch_id、基准模型版本/哈希、关联问题、受限操作、修改理由、前置条件 |
| ModelVersion | model_id、version、parent_version、变更映射、生成/审核记录 |
| RunRecord | run_id、输入/Skill/契约版本与哈希、模型参数、实际请求、响应、耗时、用量、状态 |

共同约定：

- `origin` 区分 explicit、inferred、design_extension；生成来源与审核状态分开，不允许模型自行写入 human_confirmed。
- 目标候选类别区分 goal、action、obstacle、preference、uncertain。偏好可转成有证据的质量目标，但不能机械把所有偏好排除或把所有动作改写成目标。
- source_id 沿用 `DOC023:T003` 等已有标识。引文偏移针对标准原文全文，采用 Unicode 码点半开区间，读取时保留 LF；不能混用字节偏移或 UTF-16 索引。
- Evidence 将“切片精确匹配”与“语义支持”分开记录。语义标签建议为 direct、inferred、insufficient、contradicted，并保留理由。
- 关系 label 使用 refinement、related、equivalent、none、uncertain。无序目标对只保存一条判断；refinement 额外声明 parent_id 和 child_id，图方向固定为父目标指向子目标。
- “范围/情境具体化”与严格 AND/OR 分解分开；首版不宣称已经实现 KAOS 证明或完整分解语义。
- None 表示当前材料未建立可采用关系，uncertain 表示依据不足；两者不能互换。条件性关系显式保存假设。
- ID 稳定且带文档作用域。合并、拆分、排除保留 lineage，不靠重新编号掩盖变化；补丁不能跨文档引用。
- 人工新增目标单列来源；不得伪装成源文提取结果。

## 4. 六个 Skill 的职责与验收

### 4.1 goal-extraction：目标候选提取

输入：仅包含源文和必要索引的 Document。

输出：候选清单、分类、显式/推断来源、证据候选及诊断项。此阶段不生成目标关系，不为追求数量补造目标，也不删除非目标信息。

关键判断：区分期望结果与实现动作，保留主体、情境、时间范围；采访者提问提供上下文，不能单独作为受访者愿望的直接证据。允许推断候选，但必须标记推断链。

验收：显式目标覆盖情况、无依据目标比例、类别混淆、来源标记正确性、输出合法性。先用 DOC023 建立最小流程，再运行 DOC031 和 DOC010。

### 4.2 goal-tracing：证据追溯与支持判断

输入：源文及候选或目标；可针对新增或变更对象单独运行。

输出：精确引文、全文偏移、轮次关联、语义支持等级及说明。候选证据定位失败时保留失败，不用模糊匹配结果冒充精确引文。

公共代码负责切片和定位校验，Skill 负责证据是否支持目标。重复文本无法唯一定位时利用 source_id 或保留歧义；编码残留按原文保留。

验收：引文切片一致率、轮次/说话者正确率、直接与推断区分、无支持识别。位置正确不计作语义判断自动正确。

### 4.3 goal-normalization：目标规范化

输入：带追溯结果的候选、原文及允许的建模口径。

输出：规范目标、保留/合并/拆分/排除记录、原候选到目标映射，以及需要重新追溯的对象。

关键判断：同义改写不扩展语义，合并保留情境差异；保留动作诊断。初期保守拆分，优先避免丢失目标含义。规范化后重新检查证据是否覆盖新表述。

验收：语义保真、重复处理、情境保留、映射完整、错误合并和错误拆分情况。

### 4.4 goal-refinement：关系判断与精化构建

输入：规范目标、证据和原文上下文。

输出：目标对判断清单、精化边、方向、条件及理由。首版逐文档枚举全部无序目标对，避免候选筛选误差掩盖关系能力；规模扩大后再单独评估筛选召回率。

关键判断：相关不等于精化，手段与结果不自动构成精化，等价判断反馈规范化；不能为连通图强行补边。条件不足时保留 uncertain。

验收：目标对覆盖、标签和方向、条件保留、不确定项处理。DOC023 排除设计扩展后没有已确认源文精化边，精化指标为 N/A，不能把空集正确算成高准确率。

### 4.5 model-validation：结构检查与语义疑点识别

输入：目标模型、原文、证据和契约版本。

输出：可定位的问题列表、确定性检查结果和语义审核建议。

确定性检查覆盖：契约、唯一 ID、引用存在性、跨文档引用、引文切片、自环、重复边、精化子图有向环、变更映射。相关关系不参与精化 DAG 检查。

语义检查覆盖：证据不足、错误分类、重复目标、粒度异常、可疑精化方向、情境冲突。相似度命中只构成候选疑点，不直接判语义重复；孤立目标不自动算错误。

验收：确定性缺陷检测、误报、语义问题经人审核后的有效性。报告必须区分 error、warning、needs_review。

### 4.6 model-repair：局部修复

输入：基准模型、问题列表、原文与证据。

输出：局部补丁提案及理由。应用、复检和版本写入由 Runner 完成；语义待审项进入人工队列。

首版补丁只允许必要的新增、替换、移除和证据/映射更新；每项定位对象并检查基准版本，拒绝过期或越界补丁。精确重复边等有唯一答案的问题可确定性处理；环、多种可能的关系更改和目标合并不能任意选择一个答案。

补丁在副本上事务性应用：前置条件失败或新结构错误出现则整体回滚。通过结构复检的语义修改仍标为待审核，不能自动宣布语义修复成功。

建议首版自动修复上限为 2 轮；无可应用补丁、重复模型哈希、问题无改善、触及预算或需要人工裁决时停止。该上限是待试运行调整的工程参数。

验收：问题实际消除、新增问题、原正确内容保留、修改范围、回滚和版本追溯。受控注入缺陷与真实模型错误分开计数。

## 5. 固定流程与单项隔离

建议首版固定流程：

```text
源文白名单加载 → 候选提取 → 追溯
→ 规范化 → 对变更目标重新追溯
→ 关系判断 → 验证 → 局部修复提案
→ 应用副本/复检 → 结果与待审核项
```

先在每个节点保存中间 JSON，再生成便于审核的 Markdown、证据表和 Mermaid 图。图是视图，JSON 是权威输出；图中区分条件边、候选关系和审核状态。

每个 Skill 同时支持独立运行和流程调用。测试单项能力时使用固定且来源明确的输入；测试完整链路时使用真实上游输出。两类结果分开报告，定位错误传播，避免将上游漏提取记作关系判断错误。

Runner 需要保存实际加载的 Skill 正文和参考清单。参考文件是否加载必须可核查，不允许 Skill 组多拿参考答案或专属工具。结构化输出语法重试与语义修复分别记账，首版建议语法重试最多 1 次。

## 6. 测试体系

| 层次 | 测试材料 | 验证重点 | 通过条件 |
|---|---|---|---|
| 文件与契约 | Skill 文件、Schema、引用 | frontmatter、名称、无占位符、引用可达 | 所有结构检查通过 |
| 公共逻辑 | 合成输入 | Unicode/LF 偏移、白名单、图检查、补丁事务 | 关键不变量全部通过 |
| 单项行为 | 最小合成案例和三篇开发源文 | 六类能力的实际判断 | 无来源伪造等关键违规；语义结果按 rubric 审核 |
| 链路集成 | 冻结阶段产物、离线响应、真实小样本 | 数据衔接、失败状态、断点与日志 | 输出可追溯，失败显式，参考未混入请求 |
| 对照与消融 | 冻结输入和配置 | Skill 的实际增益与成本 | 完成可比较的运行和分级报告，不预设正提升 |
| 迭代回归 | 历史失败案例及未据此修改的新案例 | 修复有效且未明显退化 | 关键违规为零，其他指标按冻结标准评审 |

最小行为案例至少覆盖：显式结果、仅动作、偏好、障碍推断、仅采访者提出愿望、否定和条件目标、重复引文、编码残留、情境差异、相关但非精化、方向颠倒、证据不足、无关系与不确定、设计扩展、引用缺失、自环/环、过期补丁、修复无改善。

确定性关键要求包括：不存在的证据不能通过；输入白名单测试不能带入参考标签；失败补丁不能写坏基准模型；模型不能自行提升人工审核等级。真实模型输出违反这些要求时应被阻断并计入失败，不通过静默删改让指标变好。

静态验证使用 skill-creator 的 quick_validate；它只检查 Skill 基本结构，不证明行为有效。行为测试检查输出含义和不变量，不依赖固定措辞或标题匹配。

## 7. 数据使用与防止评测污染

生成路径只加载 `source/` 或 `documents.jsonl` 中明确允许的字段。评测路径单独加载 `development_reference/`；`upstream_reference/` 不进入生成上下文。日志保存实际请求以供审查。

目录隔离和字段白名单只能约束 Runner 的输入构造，不能阻止拥有仓库读取工具的模型主动访问参考。因此无工具模型调用采用最小请求；若测试可读文件的 Codex Skill 行为，应使用只放必要源文、Skill 和允许资源的隔离工作区，并限制工具访问。无法限制时，不能声称实现严格防泄漏测试。

三篇开发参考已被开发过程接触，允许用于调试和口径校准，不能包装成盲测。案例用于修改 Skill 后转为开发回归案例；新验证案例单独记录，不反复查看保留测试结果来调参。

正式效果评测前，需要为储备语料补充领域/场景分组和人工参考，再冻结文档级划分；不在当前信息不足时拍定训练/测试比例。此前接触过元信息和简短上游标注的事实继续披露。若要主张严格未接触的外部泛化能力，应另建新数据集。

## 8. 对照设计和评分口径

建议分三步实验，不一次做满所有组合：

1. 单项：基础提示 vs 对应 Skill，使用相同输入和预期输出契约。
2. 组合：基础提示固定流程 vs 六 Skill 固定流程。
3. 消融：在完整 Skill 流程中逐项移除能力，检查其贡献及误差传播。

基础提示也获得任务定义、同一输出契约和必要数据，不以缺失格式说明制造弱基线。若移除某阶段的产物会使后续无法运行，预先定义兼容的透传/空产物；对无法直接可比的设置标注局限。移除模型验证能力时，外部评测器仍保留结构检查，以独立测量合法性。

冻结模型标识、调用端点和记录得到的版本信息、采样参数、可用工具、单次/整链预算、重试策略、Skill/输入哈希。预算同时报告上限与实际消耗；不能只比较调用次数。若服务支持 seed 则记录，但不承诺逐字重现。

建议先每设置单次冒烟确认可执行，再在预算确定后冻结重复次数；例如试验性使用 3 次重复，但不将其视为足够统计证据。优先同文档配对比较，报告文档级差异与波动，不能把同一文档内大量目标对当作相互独立样本。

| 能力 | 主要评分 | 重要限制 |
|---|---|---|
| 提取 | 人工语义匹配后的 precision/recall/F1、无支持率、类别混淆 | 中文改写不用精确字符串匹配；显式、推断、设计扩展分列 |
| 追溯 | 切片一致率、source_id 正确率、支持标签审核结果 | 精确匹配不替代语义判断 |
| 规范化 | 语义保真、错误合并/拆分、映射覆盖 | 不以目标越少越好 |
| 关系 | 已对齐节点上的标签结果、精化方向、uncertain 比例 | 同时报覆盖率与排除数量；缺少可评分正例时 N/A |
| 验证 | 注入缺陷检出与误报、真实语义问题确认情况 | 合成错误与真实错误分开 |
| 修复 | 经复核的修复率、新增缺陷、正确内容保留、修改规模 | 未解决和待审核不能计作成功 |
| 流程 | 完成率、结构有效率、人工介入、耗时、实际用量与费用 | 无定价依据时只报告用量，不虚构费用 |

目标匹配先制定粒度和部分匹配规则，优先进行一对一语义对齐；合并/拆分争议保留审核记录。关系同时报告“参考节点固定输入”与“预测节点端到端”结果，节点缺失或多余不能在对齐时悄悄排除。

人审关系、助手参考关系和不确定项分别报告。DOC023 的 N01 设计扩展及条件边单列；显式目标主指标不混入推断目标。现有 DOC031、DOC010 关系只能支持参考一致性分析，不能直接命名为独立人工准确率。

## 9. 修改完善与版本管理

每次迭代采用：保存失败 → 分类归因 → 最小修改 → 重跑对应案例 → 跑关键回归 → 比较新旧结果 → 冻结或撤回。

问题归因至少区分：触发范围、业务判断口径、数据契约、工具/代码、上游错误、参考分歧、模型随机性。不要把所有失败都改写成 SKILL.md 中的新禁令。

每个失败记录包含输入、实际输出、期望行为及依据、受影响版本、修改点、回归结果、是否用于调参。真实输出错误需经审核；人工标注分歧不直接转成自然错误样本。

Skill、契约、Runner、评测口径分别版本化；冻结实验保存 Git commit 与内容哈希，工作区有未提交修改时另存快照。修复模型生成新版本，不覆盖原始输出；更改数据正文须另发数据版本并重新计算偏移和哈希。

数值化语义门槛应在开发试运行后、保留评测前冻结。当前不承诺某个准确率或提升幅度；关键工程不变量要求全部通过，模型质量以实际结果和人工审核为准。

## 10. 分阶段实施与交付

| 阶段 | 建设内容 | 可审核交付物 | 进入下一阶段的条件 |
|---|---|---|---|
| A 契约与规则 | 公共 Schema、字段映射、证据与关系口径、案例规范 | 可验证样例、规则说明、版本约定 | 样例合法，关键语义边界明确 |
| B 最小运行闭环 | extraction、tracing、离线/真实适配器、单文档 Runner | DOC023 候选、证据表、请求响应与运行报告 | 引文可核验，生成输入无参考标签，失败可追溯 |
| C 规范化与关系 | normalization、refinement、变更重追溯、三篇开发运行 | 目标映射、目标对表、候选图、人工审核项 | 对数覆盖、方向和不确定项正确保存 |
| D 验证与修复 | validation、repair、事务补丁、受控错误集 | 问题报告、补丁、前后模型、复检与回滚记录 | 确定性检查通过，修复不越界，真实/注入错误分离 |
| E 单项与组合评测 | 冻结基线、Skill、消融配置和审核规则 | 可复查运行包、分级指标与失败分析 | 对照条件可比较，结论遵守数据限制 |
| F 完善与发布 | 基于失败修订、回归、发现/安装验证 | 六 Skill 冻结版本、运行入口、版本清单 | 关键不变量通过、遗留问题明确、相同配置可重新运行 |

S1 完成后再决定 S2。S2 复用同一套契约和 Skill，新增路由、有限重试与恢复；Agent 的收益必须相对已冻结的固定流程单独验证。

## 11. 推荐的第一轮实施范围

第一轮只实施 A+B：固定公共契约，创建 goal-extraction 与 goal-tracing，搭建最小 Runner，在 DOC023 上生成候选和证据报告，完成结构检查与行为审核，再到 DOC031、DOC010 检查口径是否成立。

默认工程选择是 Python、项目内维护 Skill 源码、JSON 作为权威输出、中文目标表述配英文原文引证。真实调用所用模型、凭据可用性、预算及正式评测重复次数在开始付费批量运行前落实；这些事项不阻碍先完成契约、Skill 文件和离线测试。

本方案的最终交付范围是六个可运行 Skill、公共执行设施、分层测试案例、可复查实验记录和迭代结果。现阶段能够完成开发与流程验证；正式泛化效果结论仍以补充参考标注、冻结评测设计及真实运行结果为前提。
