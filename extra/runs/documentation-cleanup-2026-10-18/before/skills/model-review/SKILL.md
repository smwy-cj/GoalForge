# 简明模型检查与人工意见处理

模型采用哪种 schema，就使用相应工具，不混用检查报告与反馈。用户只需看懂目标、层级和必要问题。程序结构检查、模型语义判断、形式证明和人工认可分别记录，不互相替代。

## KAOS

对 goalforge-kaos-1，按同级 goal-model-building 的[简明契约](../goal-model-building/references/simple-kaos.md)调用 scripts/kaos_model.py：

- inspect 核验引用、精化组成员、循环、实际附件与哈希、全文引文，重执行绑定判断并比对当前模型。缺失或篡改则拒绝。
- 语义上核对目标忠实性、精化是否足以满足父目标、必要假设、替代方案、责任和共享节点。只读取相关原文，不默认重读全部材料或重新穷举目标对。
- 关键疑点挂到目标或精化组，普通用户不阅读整份检查报告。需要进一步判断时保留问题，不删除目标掩盖缺口。
- 独立语义审查与形式化证明未实际执行时保持 not_run；不能把编制判断和机械复核当成独立质量认证。

用户在 HTML 分别对目标内容或精化组填写“可以／需修改／暂不确定”。feedback 校验当前模型 ID、版本、完整哈希、对象引用和未完成表单。部分意见可提交，没有意见的项目保持未审。

对目标修改，传播到所有相关精化组；组的争议单独重评。工具输出 revision-request.json 和原反馈记录，不直接把自然语言意见改成已验证模型。助手按待办回查资料、形成真实新判断，构建阶段重建、复检、交付。目标条件变化不能复用旧语义判断；原版本与意见保留。

新版意见包只记录分项判断与补充，没有自动完整模型认可。新版本仍 pending；用户明确总体决定应单独保留真实记录，不代填 accepted。

## 旧模型兼容

旧 goalforge-model-draft-1 继续使用[原检查与局部修复工具](references/tools.md)、[原输出契约](references/output-contract.md)和[原反馈契约](references/human-feedback.md)。旧工具只接受其旧契约，不用于新版精化组。

机械补丁使用白名单、前置条件与副本复检；修改目标或证据后相关追溯和关系失效。旧反馈不会自动迁移为新 KAOS 认可，旧交付、草稿与人工意见不覆盖。
