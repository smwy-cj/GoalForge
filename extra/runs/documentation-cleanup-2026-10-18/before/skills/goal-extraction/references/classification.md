# 候选分类与边界示例

> 旧版 draft-2 资料说明。新版不使用本表主类／子类，见 [v3 简明契约](simple-output.md)。

保留五个主类，增加 subtype；后续 Skill 可以按主类处理，人工审核可以看到更细粒度的判断。子类是操作性标签，不宣称构成形式化目标理论。

以下均为合成示例，不属于项目参考答案。分类依赖上下文；一段复合陈述可以分成多个候选并引用同一来源。

| 主类 | 子类 subtype | 示例 | 判断依据 |
|---|---|---|---|
| goal | achievement | 希望招聘人员能看到我的简历 | 期望达成的结果 |
| goal | maintenance | 团队成员应始终看到最新版本 | 期望持续维持的状态 |
| goal | quality | 查询结果应在两秒内返回 | 明确的质量要求；保留两秒 |
| goal | avoidance | 不要在夜间向我推送提醒 | 希望避免的结果；保留夜间条件 |
| action | interaction | 我先打开菜单，再点导出 | 操作步骤，未单独表达结果诉求 |
| action | workaround | 为了不漏消息，我每小时手动刷新 | 现有应对方式；不漏消息可另提目标 |
| obstacle | difficulty | 窗口缩小后按钮就看不清了 | 已发生的困难，不等于已提出方案 |
| obstacle | limitation | 只有管理员能导出，我无法完成周报 | 权限限制，可支持经说明的推断 |
| preference | solution | 如果能用邮件就更合我习惯 | 对方式的偏好；目的尚不清楚 |
| preference | experience | 我更喜欢深色界面 | 体验偏好；不凭空增加护眼收益 |
| uncertain | ambiguous | 最好更方便一点 | 缺少对象与可解释情境 |
| uncertain | constraint | 公司规定记录至少保存三年 | 明确约束，但尚需确认目标归属 |
| uncertain | proposed | 主持人提出自动提醒，用户未回应 | 提议未确认，不作受访者目标 |
| uncertain | recognition | 录音是否说“不要通知”听不清 | 识别差异可能反转含义 |

无对应子类时使用 unspecified，并写理由。子类可能重叠，选择最能解释判断的一项，其他属性放 context。

## 边界判断

### 动作与目标

“我点分享按钮，把链接复制过去”通常为 action；“我希望队友能立刻看到我修改的文档”为 goal。“希望能共享文档”若表达明确业务能力诉求可以是 goal；若只列操作而目的不明，保留 action 或 uncertain。不要使用“含动作动词就不是目标”的规则。

### 偏好与质量目标

“我喜欢邮件”为 preference；“重要决定需要用邮件正式留档”可以提取留档目标，邮件作为方式保留，不增加合规收益。“搜索最好快一点”在对象与期望清楚时可以是 goal/quality；没有阈值不得编造两秒指标。

### 障碍与隐含目标

“搜索服务太贵了”首先是 obstacle。结合明确场景可以提出“降低搜索成本”的 inferred 目标，但不得自行增加“免费”或指定新功能。无法判断是否希望改变现状时，只保留障碍或提出审核问题。

## 约束、事实与设计建议

约束先作为 uncertain/constraint 留存，待后续确认模型归属；uncertain 在此表示模型归属待定，不表示约束事实本身不确定。“我们有三名员工”等普通事实通常仅作上下文。

源资料中的提案注明提出者与是否采纳；来源明确且已采纳的要求可以是 explicit 目标。模型自行想到的改进为设计扩展，默认不生成。用户另行要求设计建议时独立交付，不混入提取集合。
